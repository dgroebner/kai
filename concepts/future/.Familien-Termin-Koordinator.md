# Implementierungskonzept: Familien-Terminkoordinator

## 1. Übersicht
Das Ziel ist die Erweiterung der bestehenden Software-Suite um ein Modul zur zentralen Aggregation und Visualisierung von Google-Kalenderdaten aller Familienmitglieder.

## 2. Architektur-Integration
Das neue Modul folgt dem bestehenden Muster (Service-Repository-Pattern), um Konsistenz zu gewährleisten.

### A. Backend-Layer (`src/Calendar/`)
*   **`CalendarClient.php`**: Verantwortlich für die Kommunikation mit der Google Calendar API unter Verwendung von OAuth2.
*   **`CalendarService.php`**: Implementiert die Geschäftslogik. Zuständig für das Abrufen der Termine, das Filtern und das Mapping der Daten aus verschiedenen Kalendern in ein einheitliches Format.
*   **`CalendarEventRepository.php`**: Verarbeitet die Persistenz (Caching) der abgerufenen Termine in der lokalen Datenbank, um API-Limits zu schonen.
*   **`SyncScheduler.php`**: Ein Cronjob-gesteuerter Dienst, der im Hintergrund die Kalender synchronisiert.

### B. API-Layer (`public/calendar/`)
*   **`api.php`**: Ein Endpoint, der als Schnittstelle für das Frontend fungiert. Er liefert aggregierte Termindaten (JSON-Format) basierend auf den Anfragen des Dashboards.

### C. Frontend-Layer (`public/js/`)
*   **`calendar-dashboard.js`**: Implementiert die Logik für das Rendern der Termine im Dashboard.
*   **UI-Integration**: Einbettung in das bestehende Web-Layout unter Nutzung des vorhandenen CSS-Frameworks.

## 3. Datenfluss-Konzept
1.  **Synchronisation**: Der `SyncScheduler` fragt in definierten Intervallen (z.B. alle 15 Min) die API aller konfigurierten Google-Kalender ab.
2.  **Aggregation**: Der `CalendarService` normalisiert die Daten (Startzeit, Endzeit, Titel, Teilnehmer, Kalender-ID).
3.  **Caching**: Die normalisierten Daten werden im `CalendarEventRepository` gespeichert.
4.  **Anfrage**: Wenn ein Nutzer das Dashboard öffnet, sendet `calendar-dashboard.js` eine Anfrage an `api.php`.
5.  **Visualisierung**: Das Frontend erhält die Daten und rendert diese (z.B. als Tagesübersicht, Wochenplan oder sortierte Liste).

## 4. Sicherheits- und Datenschutzkonzept
*   **Authentifizierung**: Die bestehende `Auth.php` sichert den Zugriff auf das Kalender-Dashboard. Nur autorisierte Benutzer (Familienmitglieder) erhalten Einblick.
*   **Datensparsamkeit**: Es werden nur relevante Daten gespeichert. Der Cache wird regelmäßig bereinigt.
*   **API-Keys**: Die Google Cloud-Credentials werden sicher in der `.env`-Datei verwaltet (analog zur bestehenden Konfiguration).

## 5. Zukünftige Erweiterung: Benachrichtigungssystem
*   **`NotificationService.php`**: Ein Dienst, der periodisch das `CalendarEventRepository` nach anstehenden Terminen durchsucht.
*   **Trigger**: Bei anstehenden Terminen wird der `MailDispatcher` genutzt, um automatisierte Zusammenfassungen (z.B. "Der Tagesplan für morgen") zu versenden.
*   **Erweiterbarkeit**: Das System ist so modular aufgebaut, dass zukünftig auch Push-Benachrichtigungen (via Webhooks oder Telegram-Bot) integriert werden können.

## 6. Meilensteine
1.  **Prototyping**: Einbindung der Google API und Anzeige der Rohdaten in einem simplen Endpoint.
2.  **Backend-Struktur**: Implementierung der Repository- und Service-Klassen.
3.  **Frontend-Integration**: Erstellung des Dashboard-Views und der JS-Logik.
4.  **Optimierung**: Implementierung des Caching-Systems und der automatischen Synchronisation.
